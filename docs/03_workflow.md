# Petal - タスク遂行ワークフロー

本リポジトリで AI エージェントがタスク（Notion の TSK-N など）に取り組む際の標準手順を定める。
個別タスクの設計・実装は、原則として本手順に沿って進めること。

## 0. 前提

- 作業開始前に [AGENTS.md](../AGENTS.md) と [docs/00_rules.md](00_rules.md) を必ず参照する。
- 既存ルールと矛盾する場合は `docs/` 側を正とする。
- ユーザーから明示の許可がない限り、破壊的 Git 操作（force push, reset --hard, branch -D 等）は行わない。

## 1. 標準手順（6 ステップ）

タスクは次の 6 ステップで進める。

**ユーザー確認ポリシー**: 確認のための停止は **Step 1（設計）の合意のみ必須**。Step 2 以降は進捗を逐次報告しながら自律的に進め、最終的な人間レビューは Step 6 で作成した PR 上で行う方針とする。設計を大きく揺るがす逸脱が生じた場合や、人間にしか答えられない情報（実機ログ等）が必要になった場合は途中でも確認を求めてよい。

### Step 1: 設計ドキュメントの作成（**ユーザー確認必須**）

- 対象タスクの設計を `docs/` 配下に Markdown で起こす。
- ファイル名は既存命名規則（例: `12_image-management.md`）に倣う。タスク ID（TSK-N）を冒頭に明記する。
- 含める項目：
  - スコープ（対象機能 / 非対象）
  - 関連する要求仕様への参照（`01_requirements.md`）
  - データモデル / API 仕様 / シーケンス（必要に応じて）
  - 既存設計（`11_*`, `12_*` 等）との差分・整合性
  - **整合性が問題となる箇所のトランザクション境界**（外部副作用と DB を同時に変える操作がある場合は [docs/00_rules.md §4](00_rules.md) の方針に従って明記）
  - 完了条件（Notion チケットの完了条件をコピーし、必要なら細分化）
- 追加したドキュメントは [AGENTS.md](../AGENTS.md) のドキュメント表にも追記する。
- **ここでユーザーへ設計を提示し、合意を得てから Step 2 へ進む**。設計レベルの判断は実装後の手戻りコストが大きいため、確認は本ステップに集約する。

### Step 2: 実装計画の策定

- Step 1 の設計に対して、具体的な実装計画を立てる。
- 計画はユーザーへ報告するが、停止して合意を待つ必要はない（重大な未確定事項がある場合のみ確認を求める）。設計ドキュメント末尾や PR 本文に残す。
- 含める項目：
  - 変更・追加するファイル一覧（backend / frontend / infra / docs）
  - 必要な migration / 環境変数 / 依存追加
  - 作業順序と各ステップの完了確認方法（型チェック、ビルド、手動動作確認など）
  - リスク・未確定事項

### Step 3: 作業ブランチの作成

- `main` から新規ブランチを切る。命名規則：
  - `feat/tsk-<番号>-<short-slug>`（機能追加）
  - `fix/tsk-<番号>-<short-slug>`（不具合修正）
  - `docs/tsk-<番号>-<short-slug>`（ドキュメントのみ）
- 例: `feat/tsk-4-user-management`
- ブランチ作成後、Step 1 / Step 2 で作成・更新したドキュメントもこのブランチで管理する（先行コミット可）。

### Step 4: 実装作業

- Step 2 の計画に沿って実装する。計画に対する逸脱・追加が必要になった場合は、計画とドキュメントを更新してから進める。
- **設計を大きく揺るがす逸脱**（DB スキーマの作り直し、API 仕様の根本変更、トランザクション境界の引き直し等）が必要になった場合は、Step 1 へ戻ってユーザーに再確認を求める。
- コミットは意味のある単位で分け、メッセージは **日本語**（[AGENTS.md](../AGENTS.md) §2）で記述する。
- 完了条件：
  - `pnpm --filter backend build` / `pnpm --filter frontend build` が通ること。
  - 設計ドキュメントの完了条件をすべて満たすこと。
  - 必要な migration が `backend/database/migrations/` に追加され、ローカルで適用できること。
  - `.env.example` の更新が必要な場合は反映すること。
  - `docs/` 内の Markdown を追加・変更した場合は `npx markdownlint-cli 'docs/**/*.md'` が通ること。

### Step 5: 自主コードレビュー

実装完了後、エージェント自身が下記観点で差分を点検し、結果をユーザーに報告する。

- **設計整合性**: Step 1 の設計と差分が一致しているか。逸脱があれば理由を明示。
- **アーキテクチャ**: オニオン依存方向（外側→内側）違反が無いか。Domain から Infra/SDK を import していないか。
- **コーディング規約**:
  - `any` 不使用、`strict` 違反なし。
  - 外部入力に Zod バリデーションが入っているか。
  - ドメインエンティティが Zod スキーマ + コンストラクタで `parse` しているか。
- **DB**:
  - 物理削除を実装していないか（必ず論理削除）。
  - migration ファイルが追加されているか。`synchronize: false` を破っていないか。
- **セキュリティ**:
  - クライアントシークレット等の秘密情報が `NEXT_PUBLIC_*` やフロントに混入していないか。
  - 認可漏れ（他ユーザー資源への到達）が無いか。
- **不要物**: デバッグログ、未使用 import、コメントアウトされた死コードが残っていないか。
- **ドキュメント**: 設計ドキュメント・`AGENTS.md` 表・`.env.example` の更新漏れが無いか。変更した `.md` ファイルに `npx markdownlint-cli 'docs/**/*.md'` のエラーが無いか。

レビューの結果、修正が必要な点があれば追加コミットで対応してから完了報告する。

### Step 6: プルリクエストの作成

Step 5 の自主レビューを通過したら、`gh` CLI でプルリクエストを作成する。

- ベースブランチは原則 `main`。
- タイトルは `<type>(tsk-N): <要約>` 形式（例: `feat(tsk-9): メールアドレス変更フローを実装`）。日本語で簡潔に。
- 本文（Markdown）は次のセクションを含める：
  - **概要**: 何をなぜやったかを 1〜3 行で。
  - **関連**: 対応 TSK-N と Notion URL（取得できる場合）、設計ドキュメント (`docs/` への相対リンク)。
  - **主な変更点**: backend / frontend / docs 等の単位で要点を箇条書き。
  - **動作確認**: 設計ドキュメント §「手動動作確認シナリオ」のチェックリストを転記し、未実施項目はチェックを外して残す。
  - **補足 / 注意事項**: マイグレーションの要否、IAM ポリシー追加、運用手順の変更などがあれば明記。

PR 作成手順：

1. ローカルブランチを `git push -u origin <branch>` でリモートへ push する。
2. `gh pr create --base main --title "..." --body "$(cat <<'EOF' ... EOF)"` で作成する。
3. 作成された PR URL をユーザーへ報告する。

注意：

- PR 作成のみで、自動マージや force push は行わない。
- ドラフト PR（`--draft`）は、未確定事項やレビュー前のシェアなど明示的な意図がある場合に限って使用する。

## 2. 例外

- 1〜2 ファイル程度のごく小さな修正（typo 修正、コメント整備等）は Step 1・2・5 をスキップしてよい。ただしブランチ作成（Step 3）、日本語コミット（Step 4）、PR 作成（Step 6）は守る。
- 既存設計を大きく揺るがす提案を行う場合は、ステップに入る前にユーザーへ方針確認を行う。
