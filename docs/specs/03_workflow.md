# Petal - タスク遂行ワークフロー

本リポジトリで AI エージェントがタスク（Notion の TSK-N など）に取り組む際の標準手順を定める。
個別タスクの設計・実装は、原則として本手順に沿って進めること。

## 0. 前提

- 作業開始前に [AGENTS.md](../AGENTS.md) と [docs/00_rules.md](00_rules.md) を必ず参照する。
- 既存ルールと矛盾する場合は `docs/` 側を正とする。
- ユーザーから明示の許可がない限り、破壊的 Git 操作（force push, reset --hard, branch -D 等）は行わない。

## 1. 全体像（7 フェーズ）

タスクは次の 7 フェーズで進める。**1〜4 はユーザーと AI の議論**、**5 は AI 単独作業**、**6〜7 はユーザー検品と後片付け**。
1〜4 で成果物のカタチを十分に詰めておくことで、5 を AI が自律的に完遂できるようにするのが本ワークフローの設計思想である。

| # | フェーズ | 主体 | 成果物 |
| --- | --- | --- | --- |
| 1 | 課題提示 | ユーザー | Notion 課題シート（タスクテンプレート） |
| 2 | 課題共有 | ユーザー + AI | 内容が確定した Notion 課題シート |
| 3 | 設計議論 | ユーザー + AI | `docs/tsk-N_<slug>.md`（設計判断ログ含む） |
| 4 | 実装議論 | ユーザー + AI | 同ファイル末尾に「実装計画」セクション追記 |
| 5 | 実装作業 | AI | コミット済みの作業ブランチ + 自主レビュー結果 |
| 6 | 評価 | ユーザー（PR レビュー） | マージ済み PR |
| 7 | 後処理 | AI | 「完了」ステータスの Notion タスク |

各フェーズの末尾には**出口判定**があり、AI がユーザーに「次フェーズへ進んでよいか」を明示的に確認する。

## 2. 各フェーズの詳細

### Phase 1: 課題提示

**主体**: ユーザー

ユーザーが Notion タスクテンプレート（タスク DB の「新規ページ」テンプレート）を使ってタスクを作成し、AI に「TSK-N に取り組む」等の指示を出す。

- Notion タスクテンプレートの項目（H2 見出しを固定）:
  - 一行サマリ
  - 背景・動機
  - 完了条件
  - スコープ外（なければ「なし」）
  - 制約（なければ「なし」）
  - 関連資料
  - 不明点・迷い（なければ「なし」）
- 完了予定日は Notion の「完了予定日」プロパティを使用（未記入可）
- 各項目は空欄可（後続フェーズで埋める）

AI は指示を受けたら **Notion タスクのステータスを「進行中」に更新**し、Phase 2 へ移行する。

### Phase 2: 課題共有

**主体**: ユーザー + AI / **必須確認: あり**

#### 入力

- Notion 課題シート

#### AI のアクション

1. `notion-fetch` で Notion タスクを取得し、各項目をパース
2. 空欄・矛盾・曖昧な点を抽出してユーザーへ質問
3. 必要に応じて関連ファイル（`docs/01_requirements.md` 等）を読み課題理解を補強

#### ユーザーのアクション

- AI の質問に回答
- 必要なら Notion ページを編集（**Phase 2 完了時点でフリーズ**、以降の更新は `docs/` 側に書く）

#### 出口判定

AI が以下を満たしたとき、ユーザーへ次の文言で確認する。

> 「課題共有フェーズの成果物が揃いました。以下を確認してください: [サマリを 5-10 行]。設計議論フェーズに進んでよろしいですか？」

チェック項目:

- [ ] 一行サマリが具体的（曖昧表現でない）
- [ ] 完了条件が**測定可能**（「動くこと」ではなく「ユーザーが X して Y を確認できる」）
- [ ] スコープ外が明示されている（「なし」明記でも OK）
- [ ] 制約が明示されている（同上）
- [ ] 不明点・迷いがゼロ、またはすべて会話で解決済み

### Phase 3: 設計議論

**主体**: ユーザー + AI / **必須確認: あり**

#### 入力

- 確定した Notion 課題シート

#### AI のアクション

1. 課題シートを読み込み、**論点を抽出**してユーザーへリストとして提示
2. 各論点について **複数の選択肢（案 A/B/C）** をメリット・デメリット付きで論点ごとに順次議論
   - 選択肢が実質 1 つしかない場合は 1 案 + 「他案を検討したが不適」と明記
3. ユーザーの判断を受けて方針確定
4. 確定内容を `docs/tsk-N_<slug>.md` に書き起こす（**判断理由を併記**）
5. Notion 課題シートの内容を `docs/tsk-N_<slug>.md` の冒頭にコピーする（リンクのみではなく実体を持つ）
6. [AGENTS.md](../AGENTS.md) のドキュメント表に追記

#### ユーザーのアクション

- AI 提示の選択肢から方針を選ぶ、または新案を提示
- 設計書をレビュー、加筆・修正を指示

#### 成果物：`docs/tsk-N_<slug>.md` の構成

```markdown
# TSK-N: <タイトル>

## 課題サマリ
（Notion 課題シートからの転記）

## スコープ
### 対象
### 対象外

## 制約

## 設計判断ログ

### 判断 1: <論点タイトル>
- **採用案**: <案の概要>
- **理由**: <なぜこれを選んだか>
- **却下案**:
  - 案 X: <概要> — 却下理由: <なぜ>

### 判断 2: ...

## データモデル（必要時のみ）
## API 仕様（必要時のみ）
## シーケンス（必要時のみ）

## トランザクション境界
（外部副作用 + DB が絡む場合は必須。docs/00_rules.md §4 に従う）

## 既存設計との差分・整合性

## 完了条件（具体化版）
- [ ] 

## 手動動作確認シナリオ
- [ ] シナリオ 1: <前提> → <操作> → <期待結果>

## 未確定事項 / リスク
```

#### 設計書のバージョン管理

ファイルを上書きしていく（git で履歴を追える）。「議論履歴」セクションは設けない。

#### 出口判定

> 「設計議論フェーズの成果物（`docs/tsk-N_<slug>.md`）が揃いました。主要な判断は次の通りです: [判断 1〜N の採用案を箇条書き]。実装議論フェーズに進んでよろしいですか？」

チェック項目:

- [ ] すべての論点に対して採用案が確定（残る未確定事項は「実装前に確定不要」と明記）
- [ ] 完了条件が実装視点で具体化されている
- [ ] 手動動作確認シナリオが書かれている（実装前にユーザー合意済み）
- [ ] 既存設計との差分が明記されている
- [ ] トランザクション境界が必要な場合、明記されている

#### 先行コミット

Phase 3 完了時点で **作業ブランチを切り、設計書を先行コミット**する。命名規則:

- `feat/tsk-<番号>-<short-slug>`（機能追加）
- `fix/tsk-<番号>-<short-slug>`（不具合修正）
- `docs/tsk-<番号>-<short-slug>`（ドキュメントのみ）

例: `feat/tsk-4-user-management`

### Phase 4: 実装議論

**主体**: ユーザー + AI / **必須確認: あり**

#### 入力

- `docs/tsk-N_<slug>.md`（設計書）
- 作業ブランチ

#### AI のアクション

1. 設計書を読み込み、実装に必要な作業を分解
2. **影響範囲のファイルを全部読む**（既存コード調査）
3. 実装計画書のドラフトを作成しユーザーに提示
4. **ドライランを実施**: 脳内で各コミットを書いてみて、決めかねる箇所（判断ポイント）をすべて洗い出す
5. ドライランで抽出した判断ポイントをユーザーへ質問し、すべて事前に解決
6. 解決内容を実装計画の「事前解決済みの判断ポイント」に記録

#### ユーザーのアクション

- 実装計画をレビュー
- 判断ポイント質問に回答
- 必要なら作業順序・コミット粒度に修正指示

#### 成果物：`docs/tsk-N_<slug>.md` の末尾に追記する「実装計画」セクション

```markdown
## 実装計画

### 変更・追加ファイル
- backend/
- frontend/
- infra/
- docs/

### 必要な migration / 環境変数 / 依存追加
- migration: 新規 / 不要
- 環境変数: `.env.example` への追加項目（不要なら「なし」）
- 依存パッケージ: 追加 / 更新 / 削除（不要なら「なし」）

### 作業順序（コミット単位）
1. **コミット 1**: <タイトル>
   - 含めるファイル:
   - 完了確認: <型チェック / ビルド / lint / 手動シナリオ X>
2. **コミット 2**: ...

### テスト方針
- 自動テスト: 書く / 書かない（理由）
- 書く場合: テスト対象 + ケース一覧

### 想定外時の判断ルール
（標準セット + タスク固有ルール。標準セットは下記「想定外時の標準ルール」を参照）

### 事前解決済みの判断ポイント
- Q: <論点> → A: <回答>
```

#### コミット粒度の方針

「意味のある単位」程度のゆるい指針（厳密化は実装中の柔軟性を奪うため）。

#### 想定外時の標準ルール（全タスク共通）

**AI 単独判断 OK の範囲**:

- 既存コードのリファクタが軽微（型定義の調整、import 整理、小さな命名修正）
- 設計書のスコープ内の追加実装

**中断してユーザーへ相談する範囲**:

- 設計書のデータモデルを変える必要が出た場合
- 設計書の API 仕様を変える必要が出た場合
- トランザクション境界を引き直す必要が出た場合
- 外部 API の仕様が想定と違った場合
- 設計書で確定した判断ログを覆す必要が出た場合

タスク固有ルールはこれに追加する形で記載。

#### 出口判定

> 「実装計画が揃いました。ドライランの結果、未解決の判断ポイントは **ありません**。実装作業フェーズに進んでよろしいですか？」

チェック項目:

- [ ] 変更・追加ファイル一覧が**ファイル名レベル**で具体化されている
- [ ] 作業順序がコミット単位で分解されている
- [ ] 各コミットの完了確認方法が明示されている
- [ ] migration / 環境変数 / 依存パッケージの要否が明記されている
- [ ] テスト方針が決まっている
- [ ] 想定外時の判断ルールがタスク固有に書かれている
- [ ] **ドライランで抽出した判断ポイントがすべて解決済み** ← 最重要

### Phase 5: 実装作業

**主体**: AI 単独 / **必須確認: なし**（ただし「想定外時のルール」に該当したら中断）

#### 入力

- `docs/tsk-N_<slug>.md`（設計 + 実装計画）
- 作業ブランチ

#### AI のアクション

1. 実装計画の作業順序通りにコミットを積む
2. 各コミットで完了確認を実行（型チェック / ビルド / lint / 手動シナリオ）
3. 「想定外時の判断ルール」に該当したら**中断してユーザーに相談**
4. lint 実行後は必ず **`git status` で未コミットの自動修正を確認**
5. コミットメッセージは**日本語**（[AGENTS.md](../AGENTS.md) §2）
6. 完了条件:
   - `cd backend && pnpm build` / `cd frontend && pnpm build` が通る
   - 設計ドキュメントの完了条件をすべて満たす
   - 必要な migration が `backend/database/migrations/` に追加され、ローカル適用可能
   - `.env.example` が必要に応じて更新されている
   - `docs/` 内の Markdown を追加・変更した場合は `npx markdownlint-cli 'docs/**/*.md'` が通る
7. 実装完了後、自分自身で**自主レビュー**を実施

#### 自主レビュー観点

- **設計整合性**: Phase 3 の設計と差分が一致するか。逸脱があれば理由明示
- **アーキテクチャ**: オニオン依存方向（外側→内側）違反なし。Domain から Infra/SDK を import していないか
- **コーディング規約**:
  - `any` 不使用、`strict` 違反なし
  - 外部入力に Zod バリデーション
  - ドメインエンティティが Zod スキーマ + コンストラクタで `parse`
- **DB**:
  - 物理削除を実装していないか（必ず論理削除）
  - migration ファイルが追加されているか。`synchronize: false` を破っていないか
- **セキュリティ**:
  - クライアントシークレット等が `NEXT_PUBLIC_*` やフロントに混入していないか
  - 認可漏れ（他ユーザー資源への到達）がないか
- **不要物**: デバッグログ、未使用 import、コメントアウトされた死コードが残っていないか
- **ドキュメント**: 設計ドキュメント・`AGENTS.md` 表・`.env.example` の更新漏れがないか。`.md` の markdownlint エラーなし

修正が必要な点があれば追加コミットで対応してから完了報告。

#### 出口判定

完了条件 + 自主レビュー観点をすべて満たした時点で Phase 6 へ。

### Phase 6: 評価

**主体**: ユーザー（PR レビュー） + AI（PR 作成・修正対応）

#### AI のアクション

1. `git push -u origin <branch>` でリモートへ push
2. `gh pr create --base main --title "..." --body "..."` で PR 作成
3. PR にラベル `author: ai` を付与（運用上の Reviewee マーカー）
4. **Notion タスクページの `PR` プロパティ（URL 型）に PR URL を書き込む**（`notion-update-page` を使用。タスク DB と PR を紐付けるための運用）
5. PR URL をユーザーへ報告

PR タイトル形式: `<type>(tsk-N): <要約>`（例: `feat(tsk-9): メールアドレス変更フローを実装`）。日本語可・簡潔に。

PR 本文（Markdown）に必ず含める:

- **概要**: 何をなぜやったか 1〜3 行
- **関連**: TSK-N、Notion URL（取得済みなら）、`docs/tsk-N_<slug>.md` への相対リンク
- **主な変更点**: backend / frontend / docs などの単位で要点
- **動作確認**: 設計書「手動動作確認シナリオ」をチェックリストで転記
- **補足 / 注意事項**: マイグレーション、IAM、`.env` 更新、運用手順変更等

#### ユーザーのアクション

- PR を確認
- 動作確認シナリオを実機で実行
- 良ければ承認・マージ
- 修正が必要なら指摘 → AI が**同 PR に追加コミット**で対応（指摘 → 修正のループ）

#### 制約

- 自動マージ・force push は行わない
- `--draft` は明示的な意図がある場合のみ
- PR 作成者（author）は技術上ユーザー本人になる（gh の認証情報による）。AI の関与は `Co-Authored-By: Claude` と PR ラベルで示す

#### 出口判定

ユーザーから「マージ完了」報告を受けた時点で Phase 7 へ。

### Phase 7: 後処理

**主体**: AI

#### AI のアクション

- Notion タスクページのステータスを **「完了」** に更新
- ローカルブランチの後始末:
  - `git switch main && git pull` で main を更新
  - **ブランチ削除はユーザー指示があった時のみ**（破壊的操作の慎重運用）

## 3. 例外（小規模タスクの圧縮ルール）

| タスク規模 | Phase 2 | Phase 3 | Phase 4 | Phase 5 ドライラン |
| --- | --- | --- | --- | --- |
| typo / コメント / 変数名リネーム | スキップ可 | スキップ可 | スキップ可 | 省略不可 |
| ファイル 1〜2 個・既存パターン踏襲 | 短縮可 | 短縮可（`docs/tsk-N_<slug>.md` は省略不可、「判断 1: 既存 ◯◯ パターンを踏襲」の 1 行でも残す） | 最小化可（変更ファイル一覧 + 1 コミット想定だけ） | 省略不可 |
| 通常タスク | 完全実施 | 完全実施 | 完全実施 | 完全実施 |

ドライラン（Phase 4 / Phase 5）は **AI の独断進行を防ぐ最後の砦** のため、規模に関わらず省略不可。

スキップする場合でも:

- Notion タスクのステータス更新（Phase 1 / Phase 7）は守る
- ブランチ作成・日本語コミット・PR 作成は守る

## 4. 用語

- **課題シート**: Phase 1 の成果物。Notion タスクページ。
- **設計書**: Phase 3 の成果物。`docs/tsk-N_<slug>.md`。Phase 4 で実装計画を末尾に追記する。
- **判断ポイント**: Phase 4 のドライランで抽出する「実装中に分岐しそうな箇所」。
- **想定外時の判断ルール**: Phase 5 で AI が単独判断 OK / 中断要相談 を切り分ける基準。
