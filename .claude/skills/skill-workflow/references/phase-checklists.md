# 出口判定チェックリスト（skill-workflow）

各フェーズ末尾の出口判定で照合する。必須確認は Phase 2 / 3 / 4 の 3 か所。
出口判定の考え方は [_shared/design-philosophy.md](../../_shared/design-philosophy.md) を参照。

## Phase 2: 課題共有（必須確認）

> 「課題共有フェーズの成果物が揃いました。以下を確認してください: [サマリ 5-10 行]。設計議論フェーズに進んでよろしいですか？」

- [ ] 一行サマリが具体的
- [ ] 完了条件が**測定可能**
- [ ] スコープ外・制約が明示されている（「なし」明記でも OK）
- [ ] 不明点・迷いがすべて解決済み

合意後、Notion 課題シートは**フリーズ**（以降の更新は `docs/` 側に書く）。

## Phase 3: 設計議論（必須確認 + ブランチ作成）

> 「設計議論フェーズの成果物が揃いました。主要な判断は: [判断 1〜N の採用案]。実装議論フェーズに進んでよろしいですか？」

- [ ] 全論点に採用案
- [ ] 完了条件が実装視点で具体化
- [ ] 手動動作確認シナリオがある
- [ ] 既存設計との差分明記
- [ ] トランザクション境界明記（外部副作用 + DB の場合は必須）

### 設計書の必須セクション（`docs/tsk-N_<slug>.md`）

課題サマリ / スコープ（対象・対象外）/ 制約 / **設計判断ログ**（採用案・理由・却下案）/ データモデル / API 仕様 / シーケンス（必要時のみ）/ **トランザクション境界**（[docs/specs/00_rules.md §4](../../../../docs/specs/00_rules.md)）/ 既存設計との差分 / **完了条件（具体化版）** / **手動動作確認シナリオ** / 未確定事項

## Phase 4: 実装議論（実行契約合格判定・最重要）

Phase 5 はサブエージェントが**質問できない状態**で実装する。本判定は「この設計書 + 実装計画だけで、会話文脈を持たない初見の AI が質問ゼロで完走できるか」を合格基準とする。

> 「実装計画が揃いました。ドライランの結果、未解決の判断ポイントは **ありません**。この設計書だけで自走可能です。実装作業フェーズ（バックグラウンド実行）に進んでよろしいですか？」

- [ ] ファイル一覧具体化（ファイル名レベル）
- [ ] 作業順序のコミット分解 / 各コミットの完了確認方法明示
- [ ] migration・環境変数・依存追加の要否明記
- [ ] テスト方針確定
- [ ] 想定外ルール（= 中断条件）がタスク固有に記載
- [ ] **判断ポイント全解決**
- [ ] **実行契約の自己テスト**（設計書を初見の別 AI に渡して追加質問なしで完走できると YES と言える）

### 実装計画の必須セクション（設計書末尾に追記）

変更・追加ファイル（ファイル名レベル）/ migration・環境変数・依存追加 / 作業順序（コミット単位 + 各コミットの完了確認方法）/ テスト方針 / **想定外時の判断ルール**（下記標準セット + タスク固有）/ **事前解決済みの判断ポイント**

### 想定外時の標準ルール（全タスク共通）

- **AI 単独判断 OK**: 軽微な既存コードリファクタ、設計書スコープ内の追加実装
- **中断して要相談**: データモデル変更、API 仕様変更、トランザクション境界変更、外部 API 想定差異、設計判断ログを覆す変更
