# Petal タスク遂行ワークフロー

このスキルは [docs/03_workflow.md](../../../docs/03_workflow.md) に定義された Petal の標準タスク遂行手順を実行するためのものである。詳細・最新の規約は必ず `docs/03_workflow.md` を参照すること（このファイルと矛盾する場合は `docs/` 側を正とする）。

## 前提（必ず最初に確認）

1. [AGENTS.md](../../../AGENTS.md) と [docs/00_rules.md](../../../docs/00_rules.md) を参照する。
2. 破壊的 Git 操作（force push, reset --hard, branch -D 等）はユーザーの明示許可なしに行わない。
3. 例外: 1〜2 ファイル程度の typo / コメント整備は Step 1・2・5 を省略可。ただし Step 3（ブランチ作成）・Step 4（日本語コミット）・Step 6（PR 作成）は遵守。

## 6 ステップの実行手順

**ユーザー確認は Step 1（設計）の合意のみ必須**。Step 2 以降は進捗を逐次報告しつつ自律的に進める。最終確認は Step 6 で作成する PR 上のレビューで行う。

例外として途中で確認を求めるのは次の場合のみ:

- 設計を大きく揺るがす逸脱（DB スキーマ作り直し、API 仕様根本変更、トランザクション境界の引き直し等）が必要になった
- 人間にしか答えられない情報（実機ログ、本番設定、外部 SaaS の状態等）が必要

### Step 1: 設計ドキュメントの作成（**ユーザー確認必須**）

- `docs/` 配下に Markdown を作成（命名: `12_image-management.md` のように既存ルールに倣い、冒頭に TSK-N を明記）。
- 必須項目:
  - スコープ（対象 / 非対象）
  - `01_requirements.md` への参照
  - データモデル / API 仕様 / シーケンス（必要に応じて）
  - 既存設計（`11_*`, `12_*` 等）との差分・整合性
  - **整合性が問題となる箇所のトランザクション境界**（[docs/00_rules.md §4](../../../docs/00_rules.md) の「DB UPDATE → 外部 API → COMMIT/ROLLBACK」原則に従う）
  - 完了条件（Notion チケットからコピーし、必要なら細分化）
- [AGENTS.md](../../../AGENTS.md) のドキュメント表にも追記する。
- 設計をユーザーへ提示し、**合意を得てから Step 2 へ進む**（このスキルで唯一の停止点）。

### Step 2: 実装計画の策定

- Step 1 の設計に対する具体的な実装計画を作成しユーザーへ提示。
- 必須項目:
  - 変更・追加するファイル一覧（backend / frontend / infra / docs）
  - 必要な migration / 環境変数 / 依存追加
  - 作業順序と各ステップの完了確認方法（型チェック、ビルド、手動動作確認）
  - リスク・未確定事項

### Step 3: 作業ブランチの作成

- `main` から新規ブランチを切る。命名規則:
  - `feat/tsk-<番号>-<short-slug>` （機能追加）
  - `fix/tsk-<番号>-<short-slug>` （不具合修正）
  - `docs/tsk-<番号>-<short-slug>` （ドキュメントのみ）
- 例: `feat/tsk-4-user-management`
- Step 1 / Step 2 の成果物はこのブランチで先行コミットしてよい。

### Step 4: 実装作業

- Step 2 の計画に沿って実装。逸脱・追加が必要な場合は計画とドキュメントを更新してから進める。
- コミットは意味のある単位で分け、メッセージは**日本語**（[AGENTS.md](../../../AGENTS.md) §2）。
- 完了条件:
  - `pnpm --filter backend build` / `pnpm --filter frontend build` が通る。
  - 設計ドキュメントの完了条件をすべて満たす。
  - 必要な migration が `backend/database/migrations/` に追加され、ローカル適用可能。
  - `.env.example` が必要に応じて更新されている。
  - `docs/` 内の Markdown を追加・変更した場合は `npx markdownlint-cli 'docs/**/*.md'` が通る。

### Step 5: 自主コードレビュー

実装完了後、エージェント自身が下記観点で差分を点検し、結果をユーザーへ報告する。修正点があれば追加コミットで対応してから完了報告。

- **設計整合性**: Step 1 の設計と差分が一致するか。逸脱があれば理由明示。
- **アーキテクチャ**: オニオン依存方向（外側→内側）違反なし。Domain から Infra/SDK を import していないか。
- **コーディング規約**:
  - `any` 不使用、`strict` 違反なし。
  - 外部入力に Zod バリデーション。
  - ドメインエンティティが Zod スキーマ + コンストラクタで `parse`。
- **DB**:
  - 物理削除を実装していないか（必ず論理削除）。
  - migration ファイルが追加されているか。`synchronize: false` を破っていないか。
- **セキュリティ**:
  - クライアントシークレット等が `NEXT_PUBLIC_*` やフロントに混入していないか。
  - 認可漏れ（他ユーザー資源への到達）がないか。
- **不要物**: デバッグログ、未使用 import、コメントアウトされた死コードが残っていないか。
- **ドキュメント**: 設計ドキュメント・`AGENTS.md` 表・`.env.example` の更新漏れがないか。変更した `.md` ファイルに `npx markdownlint-cli 'docs/**/*.md'` のエラーがないか。

### Step 6: プルリクエストの作成

Step 5 を通過したら `gh` CLI で PR を作成し、ユーザーへ URL を報告する。

- ベースブランチは原則 `main`。
- タイトル形式: `<type>(tsk-N): <要約>`（例: `feat(tsk-9): メールアドレス変更フローを実装`）。日本語可・簡潔に。
- 本文（Markdown）に必ず含める:
  - **概要**: 何をなぜやったか 1〜3 行。
  - **関連**: TSK-N、Notion URL（取得済みなら）、設計ドキュメントへの相対リンク。
  - **主な変更点**: backend / frontend / docs などの単位で要点を箇条書き。
  - **動作確認**: 設計ドキュメントの「手動動作確認シナリオ」をチェックリストで転記。未実施項目は未チェックで残す。
  - **補足 / 注意事項**: マイグレーション、IAM、`.env` 更新、運用手順変更等があれば明記。
- 手順:
  1. `git push -u origin <branch>` でリモートへ push。
  2. `gh pr create --base main --title "..." --body "$(cat <<'EOF' ... EOF)"`。
  3. 出力された PR URL をユーザーへ報告。
- 自動マージや force push は行わない。`--draft` は明示的な意図がある場合のみ。
