# Petal タスク遂行ワークフロー（7 フェーズ）

このスキルは [docs/03_workflow.md](../../../docs/03_workflow.md) に定義された Petal の標準タスク遂行手順を実行するためのもの。詳細・最新の規約は必ず `docs/03_workflow.md` を参照すること（このファイルと矛盾する場合は `docs/` 側を正とする）。

## 設計思想

- **1〜4 はユーザーと AI の議論フェーズ** → 成果物のカタチを十分に詰める
- **5 は AI 単独作業フェーズ** → ユーザーは自由になる
- **6〜7 はユーザー検品と後片付け**

各フェーズの末尾で AI が **出口判定** を行い、ユーザーへ「次フェーズへ進んでよいか」を明示的に確認する（必須確認は Phase 2 / 3 / 4 の 3 か所）。

## 前提（必ず最初に確認）

1. [AGENTS.md](../../../AGENTS.md) と [docs/00_rules.md](../../../docs/00_rules.md) を参照する。
2. 破壊的 Git 操作（force push, reset --hard, branch -D 等）はユーザーの明示許可なしに行わない。

## フェーズ進行表

| # | フェーズ | 主体 | 入力 | 成果物 | 出口判定 |
| --- | --- | --- | --- | --- | --- |
| 1 | 課題提示 | ユーザー | （ユーザー指示） | Notion 課題シート | ユーザー指示でフェーズ完了 |
| 2 | 課題共有 | ユーザー + AI | Notion 課題シート | 確定した Notion 課題シート | **必須確認** |
| 3 | 設計議論 | ユーザー + AI | 課題シート | `docs/tsk-N_<slug>.md` | **必須確認** + ブランチ作成 |
| 4 | 実装議論 | ユーザー + AI | 設計書 | 設計書末尾に「実装計画」追記 | **必須確認** |
| 5 | 実装作業 | AI 単独 | 設計+実装計画 | コミット済みブランチ + 自主レビュー | 完了条件達成で次へ |
| 6 | 評価 | ユーザー + AI | ブランチ | マージ済み PR | マージ完了報告で次へ |
| 7 | 後処理 | AI | マージ通知 | Notion ステータス「完了」 | 完了 |

## 実行手順

### Phase 1: 課題提示

ユーザーが Notion タスクテンプレートで課題を作成し、「TSK-N に取り組む」等の指示を出す。
AI は指示を受けたら **`notion-update-page` で Notion タスクのステータスを「進行中」に更新** し、Phase 2 へ移行。

### Phase 2: 課題共有（必須確認）

#### AI のアクション
1. `notion-fetch` で Notion タスクを取得し、各項目をパース（H2 見出し固定: 一行サマリ / 背景・動機 / 完了条件 / スコープ外 / 制約 / 関連資料 / 不明点・迷い）
2. 空欄・矛盾・曖昧な点を抽出してユーザーへ質問
3. 必要に応じて `docs/01_requirements.md` 等を読み課題理解を補強

#### 出口判定（ユーザー確認）
> 「課題共有フェーズの成果物が揃いました。以下を確認してください: [サマリ 5-10 行]。設計議論フェーズに進んでよろしいですか？」

チェック:
- 一行サマリが具体的
- 完了条件が**測定可能**
- スコープ外・制約が明示されている（「なし」明記でも OK）
- 不明点・迷いがすべて解決済み

合意後、Notion 課題シートは**フリーズ**（以降の更新は `docs/` 側に書く）。

### Phase 3: 設計議論（必須確認 + ブランチ作成）

#### AI のアクション
1. 課題シートから**論点を抽出**してリスト提示
2. 各論点について **複数の選択肢（案 A/B/C）をメリット・デメリット付き** で**論点ごとに順次議論**
3. ユーザーの判断で方針確定
4. `docs/tsk-N_<slug>.md` に書き起こす（**判断理由を併記**）。Notion 課題シートは**コピー**して冒頭に転記
5. [AGENTS.md](../../../AGENTS.md) のドキュメント表に追記
6. **作業ブランチを作成し、設計書を先行コミット**:
   - `feat/tsk-<番号>-<short-slug>` / `fix/...` / `docs/...`

#### 設計書の必須セクション
課題サマリ / スコープ（対象・対象外） / 制約 / **設計判断ログ**（採用案・理由・却下案を必ず記載） / データモデル / API 仕様 / シーケンス（必要時のみ） / **トランザクション境界**（外部副作用 + DB の場合は必須、[docs/00_rules.md §4](../../../docs/00_rules.md) に従う） / 既存設計との差分 / **完了条件（具体化版）** / **手動動作確認シナリオ** / 未確定事項

#### 出口判定
> 「設計議論フェーズの成果物が揃いました。主要な判断は: [判断 1〜N の採用案]。実装議論フェーズに進んでよろしいですか？」

チェック: 全論点に採用案 / 完了条件が実装視点で具体化 / 手動動作確認シナリオがある / 既存設計との差分明記 / トランザクション境界明記（必要時）

### Phase 4: 実装議論（必須確認）

#### AI のアクション
1. 設計書を読み込み実装作業を分解
2. **影響範囲のファイルを全部読む**（既存コード調査）
3. 実装計画書ドラフトを作成・提示
4. **ドライラン**: 脳内で各コミットを書き、決めかねる箇所（判断ポイント）を**すべて**洗い出す
5. 判断ポイントをユーザーへ質問しすべて事前解決
6. 解決内容を実装計画の「事前解決済みの判断ポイント」に記録

#### 実装計画の必須セクション（設計書末尾に追記）
変更・追加ファイル（**ファイル名レベル**） / migration・環境変数・依存追加 / 作業順序（コミット単位、各コミットの完了確認方法） / テスト方針 / **想定外時の判断ルール**（標準セット + タスク固有） / **事前解決済みの判断ポイント**

#### 想定外時の標準ルール（全タスク共通）
**AI 単独判断 OK**: 軽微な既存コードリファクタ、設計書スコープ内の追加実装
**中断して要相談**: データモデル変更、API 仕様変更、トランザクション境界変更、外部 API 想定差異、設計判断ログを覆す変更

#### 出口判定（最重要）
> 「実装計画が揃いました。ドライランの結果、未解決の判断ポイントは **ありません**。実装作業フェーズに進んでよろしいですか？」

チェック: ファイル一覧具体化 / 作業順序のコミット分解 / 各コミットの完了確認方法明示 / migration 等の要否明記 / テスト方針確定 / 想定外ルールがタスク固有に記載 / **判断ポイント全解決**

### Phase 5: 実装作業（AI 単独）

#### AI のアクション
1. 実装計画通りにコミットを積む
2. 各コミットで完了確認実行（型チェック / ビルド / lint / 手動シナリオ）
3. 「想定外時の判断ルール」に該当したら**中断してユーザー相談**
4. lint 後は必ず **`git status` で未コミット自動修正を確認**
5. コミットメッセージは**日本語**（[AGENTS.md](../../../AGENTS.md) §2）
6. 完了条件:
   - `pnpm --filter backend build` / `pnpm --filter frontend build` が通る
   - 設計書の完了条件をすべて満たす
   - 必要な migration が `backend/database/migrations/` に追加され、ローカル適用可能
   - `.env.example` 更新（必要時）
   - `docs/` の `.md` 変更時は `npx markdownlint-cli 'docs/**/*.md'` が通る
7. 自主レビュー実施（修正があれば追加コミット）

#### 自主レビュー観点
- **設計整合性**: Phase 3 の設計と一致
- **アーキテクチャ**: オニオン依存方向違反なし。Domain から Infra/SDK を import していない
- **コーディング規約**: `any` 不使用、`strict` 違反なし、外部入力に Zod、ドメインエンティティが Zod スキーマ + コンストラクタで `parse`
- **DB**: 物理削除なし（必ず論理削除）、migration ファイル追加、`synchronize: false` 維持
- **セキュリティ**: クライアントシークレットが `NEXT_PUBLIC_*` に混入していない、認可漏れなし
- **不要物**: デバッグログ・未使用 import・コメントアウトされた死コードなし
- **ドキュメント**: 設計書・`AGENTS.md` 表・`.env.example` の更新漏れなし、`.md` の markdownlint エラーなし

### Phase 6: 評価

#### AI のアクション
1. `git push -u origin <branch>` でリモートへ push
2. `gh pr create --base main --title "..." --body "$(cat <<'EOF' ... EOF)"` で PR 作成
3. PR にラベル `author: ai` を付与（運用上の Reviewee マーカー）
4. PR URL をユーザーへ報告

PR タイトル: `<type>(tsk-N): <要約>`（例: `feat(tsk-9): メールアドレス変更フローを実装`）。日本語可。

PR 本文セクション: **概要** / **関連**（TSK-N、Notion URL、設計書相対リンク） / **主な変更点** / **動作確認**（設計書シナリオをチェックリスト転記） / **補足 / 注意事項**

#### ユーザー指摘への対応
ユーザー指摘 → AI が**同 PR に追加コミット**で修正（指摘 → 修正のループ）。

#### 制約
自動マージ・force push なし。`--draft` は明示意図がある場合のみ。
PR 作成者は技術上ユーザー本人になる（gh 認証）。AI 関与は `Co-Authored-By: Claude` と PR ラベルで示す。

### Phase 7: 後処理

- `notion-update-page` で Notion タスクのステータスを **「完了」** に更新
- `git switch main && git pull` で main 更新
- **ブランチ削除はユーザー指示があった時のみ**（破壊的操作の慎重運用）

## 例外（小規模タスクの圧縮ルール）

| タスク規模 | Phase 2 | Phase 3 | Phase 4 | ドライラン |
| --- | --- | --- | --- | --- |
| typo / コメント / リネーム | スキップ可 | スキップ可 | スキップ可 | **省略不可** |
| ファイル 1〜2 個・既存パターン踏襲 | 短縮可 | 設計書は省略不可（1 行でも残す） | 最小化可 | **省略不可** |
| 通常タスク | 完全実施 | 完全実施 | 完全実施 | 完全実施 |

スキップ時も Notion ステータス更新 / ブランチ作成 / 日本語コミット / PR 作成は守る。
ドライランは AI の独断進行を防ぐ最後の砦のため**規模問わず省略不可**。
